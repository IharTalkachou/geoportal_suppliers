# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Streamlit web app for managing suppliers, projects, and data-provision workflows for the National Geoportal (Belarus NSDI — НИПД). Backend is PostgreSQL (Supabase-hosted), accessed via SQLAlchemy Core (raw `text()` SQL, not the ORM query layer) plus a small set of Alembic-managed models for schema tracking.

## Commands

### Run locally (Docker — primary way this app is deployed)
```bash
docker compose up -d --build          # build & start db, app, nginx, db-backup
docker compose logs -f app            # tail app logs
docker compose restart app            # restart after code change (folder is bind-mounted)
docker compose down                   # stop & remove containers
```
App: http://localhost:8501 · pgAdmin/DB access: see `.env` for credentials.

### Run locally without Docker (debugging)
```bash
pip install -r requirements.txt
streamlit run src/app.py --server.port 8501
```
**Note:** `streamlit run src/app.py` puts `src/` on `sys.path`, which is why almost every file under `src/` uses bare imports (`from config.cache import query_db`, `from ui.suppliers_tab import ...`) rather than `from src.config...`.

### Database migrations (Alembic)
Alembic is run from the **project root** (not `src/`), so `alembic/env.py` and any manually-run migration script must import via `src.config.database` / `src.models.tables` (root-relative), while the app itself imports the same modules bare (`config.database`). Both styles exist in this repo — see "Known inconsistencies" below.

```bash
alembic revision --autogenerate -m "description"   # generate migration from tables.py vs live DB diff
alembic upgrade head                                # apply pending migrations
alembic downgrade -1                                # roll back one revision
```
**Always inspect an autogenerated migration before applying it.** Alembic's autogenerate diffs `src/models/tables.py` against the live DB schema — if a table/column/index/comment exists in the DB but isn't declared in `tables.py`, autogenerate will propose *dropping* it. This has already happened once in this repo: an incomplete `tables.py` produced a migration that would have deleted 13 real indexes and every column/table comment. Read the generated `upgrade()`/`downgrade()` body; if it contains `drop_index`/`comment=None` changes you didn't intend, the fix is to update `tables.py` (add the missing `Index(...)` / `comment=...`) and regenerate, not to hand-edit the migration.

There is no test suite and no lint/build step configured in this repo.

## Architecture

### Request/session lifecycle
1. `src/app.py` is the sole entrypoint. It calls `load_settings()` (DB-backed feature flags: maintenance mode, session timeout), then handles auth.
2. **Auth is not Streamlit's built-in session state alone** — it's backed by a custom file-based token store (`config/session_store.py`) so login survives page refresh (`Ctrl+R`) and browser reopen within a timeout window. Tokens are stored as JSON files under `SESSION_DIR` (`app_data/sessions/` in Docker), keyed by a UUID passed via `st.query_params["session"]`. Each token file also carries a browser/OS fingerprint + IP; mismatches are logged as `SESSION_HIJACK_ATTEMPT` but the original session is *not* invalidated (only that request is denied).
3. `config/session_store_2.py` is an **older, simplified variant** of the same module (no IP check, no `sync_session_to_disk`, different signatures). `app.py` imports from `session_store` (not `_2`) — treat `_2` as dead code unless told otherwise.
4. Navigation is a flat `st.segmented_control` with 5 top-level sections wired in `app.py`: Поставщики (`suppliers_tab`), Наборы (`datasets_tab`), Проекты (`project_dashboard`), Заявки (`requests_tab`), Аналитика (`analytics_tab`). An admin panel (`admin_panel.py`) is reached via a header button, gated by `require_role("admin")`.
5. Every DB read goes through `config/cache.py::query_db()`, wrapped in `@st.cache_data(ttl=120)`. Every write path follows the same shape: build params → `session.execute(text(sql), params)` → `session.commit()` → `clear_cache()` → `st.rerun()`. `clear_cache()` must be called after commit or stale cached reads will be shown.

### Data model: raw SQL vs ORM
Almost all business logic uses **raw parameterized SQL** via `sqlalchemy.text()`, not the ORM session query API. `src/models/tables.py` exists mainly so **Alembic** can autogenerate migrations — it is kept in sync with the live schema (34 tables, custom Postgres ENUMs, arrays, indexes, comments) but is barely used at runtime (only `AppSetting` and `AuditLog` are actually imported/queried as ORM classes, in `settings_handler.py` and `maintenance.py`). When adding a column/table, update **both** the live DB (via an Alembic migration) and `tables.py` — they are the source of truth for autogenerate diffing, not for query logic.

Custom Postgres ENUM types (`applicant_category`, `org_target_type`, `request_status`, `data_provision_type`, `restrictions`, `definitions`) are defined with `create_type=False` in `tables.py` because they already exist in the DB and are cast explicitly in raw SQL (`CAST(:val AS applicant_category)`) rather than created/managed by SQLAlchemy.

### The "single stages table" refactor
Project stages used to be split across a bureaucracy-specific table and a technology-specific table; they were later merged into one shared `project_stages` table (see git history: "объединение стеков в одну таблицу"). The distinction between the two tracks is now done at the *data* level, not the schema level:
- `stages.track_category` = `'1. Документарный'` (bureaucracy) or `'2. Технологический'` (technology).
- For technology-track rows, `project_stages.affected_item_ids` (JSONB array) lists which `project_items.item_id` the stage applies to — queried via `jsonb_array_elements_text(...)::int` / `CROSS JOIN LATERAL`.
- `item_stages_old` is the **pre-refactor** technology-stage table, kept only for historical FK references from `stage_documents`; it is not written to by current code.
- `bureaucracy_tab.py` and `technology_tab.py` both operate on `project_stages` with near-identical auto-iteration/auto-close logic (`_resync_buro_iterations` / `_resync_tech_iterations`), filtered by `track_category` — read both together when changing this logic, they tend to drift.
- `utils/project_utils.py::sync_project_status()` recomputes `projects.status` from the current state of `project_stages` after every stage save; it's called explicitly after each CRUD, not via a DB trigger.

### Reactive CRUD pattern
Tables/forms across `suppliers_tab.py`, `datasets_tab.py`, `project_dashboard.py`, `bureaucracy_tab.py`, `technology_tab.py` follow the same shape: a filterable `st.dataframe` for browsing, plus `@st.dialog(...)`-based modal forms for create/edit (see `bureaucracy_tab.py::stage_mgmt_dialog` for the fullest example — auto-computed `planned_end` from stage duration, dependent staff/document sub-sections). Prefer this `st.dialog` pattern over inline forms when adding new CRUD screens — it's what the rest of the codebase does.

### Analytics module (`src/ui/analytics/`)
`analytics_tab.py` is a thin router; the actual logic is split by concern:
- `data_provider.py::get_analytics_snapshot()` — single cached query that UNIONs bureaucracy-track and technology-track stage rows (expanding `affected_item_ids` for the latter) into one flat DataFrame. Most analytics views consume this instead of writing their own joins.
- `kpi_logic.py` — task-level KPI cards/grouping (SLA proximity coloring, badges).
- `calendar.py` — `streamlit_calendar` deadline view.
- `staff.py` — per-employee workload views.
- `progress_math.py` — progress % calculations per track (`calculate_buro_progress`, `calculate_tech_progress`, `calculate_project_progress`) and the "traffic light" summary chart.
- `heatmap.py` — detailed delay heatmaps (referenced as still-in-progress in `analytics_tab.py` comments).
- `reports.py` — exports/registries (agreement registry, meeting minutes, Excel exports).
- `report_docx.py` — monthly NIPD report builder (`.docx` generation via `python-docx`). Report sections/blocks are stored as JSONB in `reports_monthly.sections_data`, driven by the `DEFAULT_SECTIONS` template dict at the top of the file. Once a report is fixed (`fixed_at` set via the "Зафиксировать" dialog), it becomes read-only; `get_report_period_bounds()` uses the previous report's `fixed_at` (or the 1st of the month if none) as the start of the next collection period — this is load-bearing logic, don't change the fixing flow without checking it.
- `analytics_tab.py::_sync_overdue_log_internal()` runs on every load of the Analytics tab: it inserts newly-overdue stages into `overdue_log` (`ON CONFLICT DO NOTHING`, so it's idempotent) for both tracks.

### Known inconsistencies to be aware of
- **Import style split**: most of `src/` uses bare imports (`config.*`, `models.*`, `ui.*`) because Streamlit runs with `src/` as the path root. But `src/utils/maintenance.py` and `alembic/env.py` use root-relative imports (`src.config.*`, `src.models.*`) because they're invoked from the project root. If you add a new module that needs to work in both contexts, check how it's actually invoked rather than copying a neighboring file's import style.
- `requirements.txt` is saved as UTF-16 — reading it with a plain UTF-8 tool may render it unreadable; decode as UTF-16 if you need to parse it programmatically.
- There are two Dockerfiles: `dockerfile` (dev, used by `docker-compose.yml`) and `dockerfile copy for prod` (used by `docker-compose.prod.yml`) — check which compose file you're targeting before editing build steps.

## Auth & roles
Three roles, hierarchical: `user` < `editor` < `admin` (see `config/auth.py::require_role()`). Role gates are enforced per-render-function (e.g. `render_admin_panel` calls `require_role("admin")` at the top), not via a central router — new admin-only screens must call this themselves.

All login/logout and CRUD actions that call `log_action()` write to `audit_log` over a **separate** DB session/connection from the business transaction, so audit writes never roll back with a failed business transaction and never block it on error (failures are swallowed and printed to stderr).

Изменения в `src/ui/bureaucracy_tab.py` и `src/ui/technology_tab.py` (пересчёт итераций одноимённых этапов, форма управления этапом):
- **Разделение пересчёта итераций по трекам**: `_resync_buro_iterations()` раньше пересчитывала `iteration_count` для *всех* `project_stages` проекта (без фильтра по `track_category`), из-за чего каждое сохранение/удаление бюрократического этапа лишний раз перезаписывало `iteration_count` и у технологических этапов того же проекта. Теперь она джойнится на `stages` и фильтрует `track_category = '1. Документарный'`, симметрично уже существующей `_resync_tech_iterations()` (`track_category = '2. Технологический'`).
- **Порядок итераций при равных датах**: сортировочный ключ в обеих функциях был одной датой (`actual_end`/`planned_start`/`actual_start` в зависимости от `micro_status`), из-за чего при совпадении дат у двух записей одного этапа (например, у завершённой итерации `actual_end` совпадает с `actual_start` следующей) порядок определялся нестабильно, по случайному порядку возврата строк из БД. Ключ заменён на кортеж `(primary_date, start_date)`, где `start_date = actual_start or planned_start` — тай-брейк по дате старта разруливает конфликт. Если в будущем понадобится поддержать вставку итерации «задним числом» с датой строго между двумя существующими записями — эта сортировка справится (в отличие от варианта с `stage_progress_id` как вторичным ключом, который отражает только порядок создания записи в БД, а не её логическую хронологию).
- **Залипание полей формы**: кнопка «✏️ Редактировать» открывала `stage_mgmt_dialog`/`tech_mgmt_dialog` без очистки `st.session_state` ключей формы (`d_*`/`td_*`). Поскольку виджеты диалога используют статичные `key=`, Streamlit не переприменяет `value=` для уже существующего в session_state ключа — при последовательном открытии формы для разных этапов поля показывали данные от первого открытого этапа, а не от текущего. Кнопка теперь удаляет эти ключи перед открытием диалога — тот же паттерн, что уже применялся у кнопки «➕ Добавить этап»/«➕ Тех. этап».
- **Блокировка полей «Факт. начало»/«Факт. конец»**: для статусов `micro_status IN (1, 5)` («Планируется»/«Отложено») эти поля теперь принудительно сбрасываются в `None` и рендерятся с `disabled=True` — раньше можно было проставить фактическую дату старта заранее, до того как этап реально начался, что искажало сортировку итераций (см. пункт выше) и здравый смысл данных. Поля становятся активными автоматически при выборе любого другого статуса.

Если Alembic обычно гоняют внутри Docker-контейнера (`docker compose exec app alembic ...`), это может быть не нужно — не проверялось в этой сессии.

### Row Level Security (RLS) на Supabase
Все 34 таблицы `public`-схемы (плюс `alembic_version`) имеют `ENABLE ROW LEVEL SECURITY` **без единой политики** (миграция `4c9745be22b9_enable_row_level_security_on_all_public_.py`) — это закрывает Supabase PostgREST API (роли `anon`/`authenticated`) от прямого доступа к данным, минуя приложение. Это **не влияет** на работу самого приложения: роль `postgres`, от имени которой подключается и локальный, и HF Space инстанс (`DATABASE_URL`), владеет всеми таблицами и имеет `rolbypassrls = true` — RLS для нее полностью прозрачен, проверено вживую (SELECT/UPDATE на RLS-таблице без политик прошли без ошибок). Если когда-то появится второй канал доступа к БД (не через текущий `DATABASE_URL`/роль `postgres`) — для него RLS-политики придётся создавать явно, иначе доступ будет запрещён по умолчанию.

Отдельно: view `public.v_bi_flat_export` (ручная BI-выгрузка из `db/schema.sql`, не используется кодом приложения) переведена на `security_invoker = true` (миграция `3dfa3c81c583_set_security_invoker_on_v_bi_flat_.py`) — без этой опции view по умолчанию выполняется с правами создателя (`SECURITY DEFINER`), что обходит RLS-политики любой вызывающей роли.

### Заявки о включении в НИПД (`src/ui/inclusion_requests_tab.py`)
Третий, отдельный от `reg_requests`/`provision_requests` механизм заявок — реализует п.7 Положения о НИПД (Постановление Совета Министров №32 от 16.01.2024): добровольное включение в Национальную инфраструктуру пространственных данных набора, не входящего в перечень обязательных. Подключён в `requests_tab.py` как третий пункт навигации «🗂️ Включение в НИПД» (форма подачи + реестр), с собственным треком этапов `stages.track_category = '5. Заявка на включение в НИПД'` (`INCL_SUBMITTED → INCL_REVIEW → INCL_APPROVED/INCL_REJECTED → [INCL_DISPUTE] → INCL_PUBLISHING → INCL_CLOSED`, миграция `636d01f3cff0_add_inclusion_requests_workflow_tables.py`), с SLA-блоком в карточке заявки по тому же паттерну, что и `provision_requests` (`add_business_days`, 15/10 раб. дн.).
- **Схема**: `inclusion_requests` (поставщик, `project_id` nullable, `dataset_id`/`info_id`, источник/состав/территория, вид действия, ссылка, вариант доступа, `status_id`, `previous_request_id` — цепочка повторных подач после доработки, `published_at` — дата вехи публикации) + `inclusion_request_history` (воронка, копия структуры `provision_request_history`). `stage_documents.inclusion_history_id` добавлен для будущего прикрепления документов к этапам (UI пока не использует).
- **Связь с проектами**: при подаче заявки поставщик и проект выбираются/создаются сразу (проект — один из существующих проектов поставщика или новый). Отказ от прямой автогенерации бюрократических/технологических этапов в `project_stages` для этого проекта — сознательное решение, отложено на будущее.
- **Форма подачи**: набор/вид сведений можно (а) выбрать из состава уже существующего `project_items` выбранного проекта — сужает список до того, что реально в проекте, (б) выбрать из полного справочника `datasets`/`info_types`, (в) создать новые прямо в форме (создание нового `dataset` + `info_type` одновременно — штатный сценарий). Дата/время подачи — явный `date_input`/`time_input` в форме (пишется в `created_at`), а не `server_default now()`, чтобы можно было указать более раннюю фактическую дату поступления заявки.
- **Воронка**: отказ (`INCL_REJECTED`) ветвится на «повторная подача» (создаёт новую запись `inclusion_requests` с `previous_request_id`, возвращается на `INCL_SUBMITTED`) или «спор в Госкомимущество» (`INCL_DISPUTE`, 10 раб. дн., решается в пользу поставщика — назад на `INCL_APPROVED`, или подтверждает отказ — назад на `INCL_REJECTED`). `INCL_PUBLISHING` — намеренно долгоживущий этап (пока идёт согласование/работа по связанному проекту), закрывается кнопкой «Опубликовано» (фиксирует `published_at`) и сразу переводит в `INCL_CLOSED`.
- **Обратная связь из карточки проекта**: `suppliers_tab.py::render_datasets_subtab()`, колонка «📦 Состав наборов» — под каждой карточкой набора/вида сведений подгружаются связанные `inclusion_requests` этого проекта (по совпадению `info_id`, не по `item_id`, т.к. заявка может быть подана до появления `project_items`) и рендерятся кнопкой-переходом прямо к нужной заявке в реестре.
- **Ручная перенумерация**: после первой реальной заявки её `req_id` был вручную перенумерован с 2 на 1 (тестовая транзакция с откатом заранее заняла значение 1 в sequence — `nextval()` не откатывается вместе с транзакцией). Если понадобится сделать это снова: FK не deferrable, поэтому нельзя просто `UPDATE req_id` у родителя раньше детей — рабочий способ: вставить копию родительской строки с нужным `req_id`, перевесить FK у дочерних записей, удалить старую родительскую строку, затем `setval(...)` на sequence.

### `st.segmented_control` с `default=` и программной установкой session_state — конфликт
Если у виджета одновременно задан `default=` и его `key` может быть выставлен извне (например, кнопкой-переходом из другого раздела через `on_click`-колбэк, пишущим `st.session_state[key] = ...`), Streamlit не подставит новое значение из `default` (он игнорируется, когда ключ уже в session_state), но это комбинация всё равно нежелательна и матчит паттерн, которого в проекте принято избегать. Верный паттерн — тот же, что уже используется для `main_nav` в `app.py`: `if key not in st.session_state: st.session_state[key] = <default>` **до** вызова виджета, без `default=` в самом вызове. Это же было исправлено для `req_main_nav`/`incl_main_nav`, когда добавлялась кнопка-переход «к заявке» из карточки проекта. Отдельно: если селектбокс использует `index=` для программного выбора элемента (как выбор конкретной заявки в реестре по `sel_incl_id`), при повторном заходе на экран Streamlit не переприменит `index=`, если у виджета уже есть значение в session_state под его `key` — тот переход-колбэк должен явно делать `st.session_state.pop(widget_key, None)` перед сменой навигации (см. `go_to_incl_cb` в `suppliers_tab.py`).

### Реестр учётных записей пользователей (`src/ui/analytics/reports.py`) и настройка `total_registered_accounts`
Новый 7-й пункт в «Аналитика → Отчёты»: `_render_accounts_registry()`. Формирует текст в фиксированном формате («По состоянию на ДД.ММ.ГГГГ заведено X учётных записей, в частности: Z для A юридических лиц...») плюс экспорт в `.docx` (`_build_accounts_registry_docx()`, тем же паттерном `python-docx`/Times New Roman, что и `report_docx.py`).
- **X** (общее число учётных записей) — новая ручная настройка `total_registered_accounts` в `app_settings` (JSONB), добавлена в `DEFAULT_SETTINGS` (`settings_handler.py`) и как `st.number_input` в `admin_panel.py::_render_system_settings`. Вводится вручную «по данным Keycloak» до появления прямой интеграции с БД Keycloak — **уже включает** учётные записи Оператора.
- **Y** (физлица) = число завершённых заявок `reg_requests` с `applicant_type = 'Физическое лицо'` (`status = 'Завершена'`) — без дедупликации, одна заявка физлица гарантированно даёт одну учётку.
- **A/списки юрлиц** = уникальные `applicant_name` среди завершённых заявок `applicant_type = 'Юридическое лицо'`, сгруппированные с приоритетом «Поставщик» (если организация хоть раз подавала заявку с `org_type = 'Поставщик'` — попадает в список поставщиков, иначе в список пользователей портала).
- **Z = X - Y** (учётных записей юрлиц) — вычисляется на лету, не хранится.
- **Оператор** (ГП "Белгеодезия", константа `OPERATOR_NAME` в `reports.py`) в `reg_requests` не фигурирует (его не регистрируют через обычную заявку), поэтому добавлен вручную: **+1** к счётчику A и первой строкой в список поставщиков. В Z **не** участвует — X уже вводится с учётом его учётки(ок).
- Метрики X/Y/Z **не** выводятся в UI отдельными цифрами (сознательно убрано по требованию) — только сам текстовый блок отчёта и кнопка экспорта.

### Переработка `calculate_tech_progress` (`src/ui/analytics/progress_math.py`) — воронка была короче реального списка этапов
Расчёт прогресса технологического трека (используется в «Аналитика → Прогресс проектов → Сводный прогресс по проектам», `render_traffic_light_chart`) считал только 11 из 18 реальных `stage_code` трека `'2. Проекты, застрявшие на любом из этих этапов, показывали заниженный/нерелевантный процент, потому что формула просто «перепрыгивала» от блока Admin/Testing сразу к блоку META, как будто между ними ничего нет.

Каждый шаг весит `95% / 16 ≈ 5.94%`, оставшиеся фиксированные **5%** — бонус за зарегистрированного активного администратора поставщика (как и раньше).
- `NG_CONSULT` и `TECH_SUPPORT` **сознательно исключены** из расчёта % — это повторяющиеся консультационные этапы (см. блок 08 отчёта НИПД, `fetch_moderation_stats()` в `report_docx.py`), не блокирующие и не продвигающие воронку готовности набора.
- Авто-зачёт пропущенных промежуточных шагов сохранён (если стадии нет в `project_stages`, но есть более поздняя по `TECH_FUNNEL_CODES` — ранняя считается пройденной).
- Заодно исправлена **дедупликация строк**: `get_analytics_snapshot()` разворачивает `project_stages.affected_item_ids` через `CROSS JOIN LATERAL jsonb_array_elements_text(...)`, из-за чего одна итерация технологического этапа, затрагивающая N наборов данных, попадает в снапшот N одинаковыми строками — искажало `done_count`/`total_count`. `calculate_tech_progress` теперь делает `df.drop_duplicates(subset=['stage_code', 'iteration_count'])` в начале.
- `render_tech_audit_table` (аудит-таблица за тумблером «🔍 Отладка» на той же странице) обновлена на тот же список `TECH_FUNNEL_CODES + ['NG_CONSULT', 'TECH_SUPPORT']`, чтобы не расходиться со scoring-логикой.
- **Бюрократический трек в этой переработке не трогали** — `calculate_buro_progress()` использует другую, более сложную ветвящуюся state-machine (блок Б для `CHANGES_PROTOCOL`/`ADDITIONAL_AGREEMENT`, проценты 90/50/45/25/5 по блокам), чтобы не смешивать риски двух разных переписываний. **Обновление**: `CHANGES_PROTOCOL` и `PROTOCOL_NEGOTIATIONS` с тех пор получили полноценную функциональность (не просто отложены) — см. «Гибкое завершение бюрократического трека» и «Этапы работы над документом» ниже. Ветка Б самой формулы процента (90/50/45/25/5) по-прежнему не менялась.

### Known issue: парадоксальный порядок `iteration_count` при пересчёте (`_resync_buro_iterations`/`_resync_tech_iterations`)
`get_sort_key()` внутри обеих функций (идентичный код в `bureaucracy_tab.py:29-33` и `technology_tab.py:29-33`) берёт **разную по смыслу** дату как primary-компонент ключа сортировки в зависимости от статуса итерации:
- `micro_status == 4` («Выполнено») → `(actual_end, actual_start)` — primary это дата **завершения**.
- `micro_status == 1` («Планируется») → `(planned_start, ...)`.
- всё остальное («В работе», «Ожидание», «Отложено», «Просрочено») → `(start, start)`, где `start = actual_start or planned_start` — primary это дата **начала**.

Поскольку `actual_end` завершённой итерации и `start` следующей активной итерации — это две разные точки временной оси, а не одна и та же величина, их прямое лексикографическое сравнение не гарантирует хронологический порядок. Конкретный воспроизводимый парадокс: если завершённая итерация стартовала и закрылась в один день (`actual_start == actual_end`, частый случай для формальных/мгновенных этапов), её ключ `(D, D)` может оказаться **больше**, чем ключ другой, ещё активной итерации того же этапа, стартовавшей раньше (`(D-n, D-n)`) — активная получает более поздний `iteration_count`, чем завершённая, хотя по смыслу должно быть наоборот. Это напрямую влияет на «Аналитика → Прогресс проектов»: формулы в `progress_math.py` (`calculate_buro_progress`/`calculate_tech_progress`) берут «последнюю итерацию» через `.loc[df['iteration_count'].idxmax()]`, так что неверный номер итерации подсовывает не ту строку.

Найдено и подтверждено (см. историю чата), **сознательно не исправлено** — пользователь попросил дать время подумать над правильным решением, прежде чем менять логику пересчёта итераций (затрагивает обе вкладки этапов и потенциально исторические данные при повторном пересчёте существующих проектов).

### Гибкое завершение бюрократического трека: `project_documents` и `project_document_stages`

Раньше факт подписания бюрократического трека выражался единственным этапом `CONTRACT_SIGNED` («Документ подписан»), а вид документа (соглашение/протокол) определялся только флагом проекта `projects.is_agreement_project` — то есть проект содержал ровно один подписываемый документ. Реальность иная: соглашение может быть подписано первым, а работа над одним или несколькими протоколами продолжаться отдельно; у одного набора данных виды сведений могут закрываться разными протоколами частично (напр. УИВП Минобороны, Национальное агентство по туризму — см. `Отчет 04-09-2026.pdf`, не хранится в репозитории).

- **Модель**: `project_documents` (`doc_id`, `project_id`, `doc_kind` — `'Соглашение'` | `'Протокол'`, `doc_number`, `doc_url`, `is_signed`, `signed_date`, `signed_stage_id` — FK на `project_stages.stage_progress_id`, этап, где документ подписан). Частичный уникальный индекс `idx_pdocs_one_agreement` не даёт завести больше одного «Соглашения» на проект; протоколов — сколько угодно. Охват документа — `project_document_items` (`doc_id`, `item_id`, `part_id` nullable): **пустой охват = документ покрывает весь проект** (обычный случай, заполнять не нужно); заполняется только когда протокол закрывает не все виды сведений набора. ⚠️ `project_item_parts` (части в составе проекта) с тех пор **удалена** — части переехали в справочник, см. «Части вида сведений» ниже; `part_id` теперь ссылается на `info_type_parts`.
- **Этап `CONTRACT_SIGNED`** в `stage_mgmt_dialog` (`bureaucracy_tab.py`) даёт мультиселект документов проекта — на одном этапе можно подписать сразу несколько (соглашение + протокол, либо несколько протоколов). При статусе «Выполнено» отмеченные документы получают `is_signed=true`/`signed_date`; сохранение сначала снимает `signed_stage_id` со всех документов, ранее привязанных к ЭТОМУ этапу, затем проставляет заново по текущему выбору.
- **Прогресс бюро-трека** (`calculate_buro_progress`, блок А.1, `progress_math.py`): раньше `CONTRACT_SIGNED` со статусом «Выполнено» сразу давал 100%. Теперь, если у проекта заведены `project_documents`, прогресс = `100 * подписано / всего` (100% только когда подписаны все документы); проекты без заведённых документов считаются по-старому — обратная совместимость. Счётчики `docs_total`/`docs_signed` читаются из `get_analytics_snapshot()` (`data_provider.py`) как два скалярных подзапроса в бюрократической ветке UNION (технологическая ветка отдаёт `NULL`). `sync_project_status()` (`project_utils.py`) аналогично считает проект «подписанным» только когда подписаны все его документы, а не по одному закрытому `CONTRACT_SIGNED`.
- **Отчёт «9. Сводный отчёт о Поставщиках Национального геопортала»** (`reports.py::_render_supplier_projects_summary`, ранее назывался «Сводная таблица по поставщикам и проектам») переработан под форму реального регламентного отчёта: строка = вид сведений (или его часть, если заведена), а не проект. Колонка «Протокол» = есть ли подписанный документ `doc_kind='Протокол'`, покрывающий этот item — явно через `project_document_items` либо неявно (пустой охват). Флаги «Данные/Метаданные получены/опубликованы» развёрнуты по набору через `affected_item_ids` с обязательной дедупликацией (`jsonb_array_elements_text` + `DISTINCT`/`GROUP BY` — один этап на N наборов иначе даёт N одинаковых строк).
- **⚠️ Известное расхождение**: месячный отчёт НИПД (`report_docx.py`, блоки 12/13, `fetch_bureaucracy_logic_stats`) **не переведён** на новую модель — там по-прежнему проверяется закрытый этап подписания + флаг `is_agreement_project`, без учёта `project_documents.is_signed`. Проект может показывать «подписано» в месячном отчёте и одновременно «в работе» (не 100%) в прогрессе/отчёте №9, если не все документы проекта подписаны. Расхождение не устранялось и не проверялось на реальных данных — при следующей правке любого из двух отчётов свериться с другим. (Коды этапов в блоках 11/13 с тех пор расширены до протокольных — см. «Разделение этапов по типу проекта» ниже, — но сама проверка по `is_signed` так и не добавлена.)

### Документы этапов: `stage_documents` теперь несёт и протокол переговоров, и обычные вложения

`stage_documents.doc_url` стал nullable (документ можно завести до появления скана), добавлены `doc_date` (дата документа) и `is_nego_protocol` (bool). Протокол переговоров (веха этапа `NEGOTIATIONS`, чекбокс «Есть протокол переговоров» в диалоге этапа) — **другая сущность**, чем протокол передачи данных (`project_documents`): не покрывает виды сведений, не участвует в расчёте прогресса, поэтому живёт в `stage_documents` с флагом `is_nego_protocol=true`. Общий список «📂 Документы» в форме этапа фильтрует `is_nego_protocol = FALSE`, иначе документ дублировался бы в двух местах.

Этап `PROTOCOL_NEGOTIATIONS` был переименован из «Протокол переговоров» в «Согласование протокола» (миграция `c9f4a2071e58`) — он дублировал сущность, которую теперь явно моделирует флаг у `NEGOTIATIONS`. Существующие записи этого этапа с прикреплёнными сканами не удалялись вслепую: сканы помечены `is_nego_protocol=true` и перенесены на последнюю итерацию этапа `NEGOTIATIONS` того же проекта; если в проекте нет `NEGOTIATIONS` — запись этапа и её сканы остались нетронутыми, для разбора вручную.

### Этапы «Согласование протокола» (`PROTOCOL_NEGOTIATIONS`) и «Внесение изменений в протокол» (`CHANGES_PROTOCOL`) — работа над документом до/после подписания

Оба этапа выражают работу над документом `project_documents`, но не через колонку в самом документе (как `signed_stage_id`), а через **таблицу-связку** `project_document_stages` (`doc_id`, `stage_progress_id`, плюс у сценария изменений: `is_ready`, `new_url`). Это принципиально: работа над одним и тем же протоколом ведётся **итеративно** — несколько итераций этапа, каждая своя строка `project_stages`. Ранняя реализация хранила связь как `project_documents.drafting_stage_id` (один-к-одному) — из-за этого повторное указание документа во второй итерации стирало его из первой (баг, найденный пользователем вживую; исправлено миграцией `e7b2d40a91c3`, заменившей колонку на таблицу-связку).

- **`PROTOCOL_NEGOTIATIONS`** («Согласование протокола»): мультиселект документов проекта (любых, включая соглашение), без влияния на `is_signed`/`signed_date` — просто фиксирует, над чем идёт работа. Охват каждого документа показывается прямо в подписи мультиселекта (из `project_document_items`).
- **`CHANGES_PROTOCOL`** («Внесение изменений в протокол»): к выбору доступны **только** уже подписанные протоколы со сканом (`doc_kind='Протокол' AND is_signed AND doc_url` не пусто) — соглашение исключено по смыслу названия этапа, а неподписанный/бессканный документ менять нечего. Для КАЖДОГО выбранного протокола отдельно: чекбокс «✅ Готов» + (если отмечен) поле новой ссылки. Как только протокол отмечен готовым с указанной ссылкой — `project_documents.doc_url`/`signed_date` обновляются **немедленно** при сохранении формы, не дожидаясь закрытия всего этапа (на одном этапе изменений может идти несколько протоколов с разной готовностью). Общий блок «➕ Добавить/изменить документ» (все документы проекта) для этого этапа скрыт — нужны только уже выбранные протоколы.
- В карточке этапа (`render_stage_card`) документ без готовности на `CHANGES_PROTOCOL` показывается **текстом без ссылки** — «Протокол N (изменяется)» (старый скан уже неактуален, показывать его смысла нет); готовый — кликабельной ссылкой «Протокол N (готов, с изменениями)» на уже обновлённый `doc_url`. На `PROTOCOL_NEGOTIATIONS` — как раньше, ссылка с пометкой «(в работе)».
- Динамические per-документные ключи session_state (`d_ready_<doc_id>`, `d_newurl_<doc_id>`) не входят в статичный список `STAGE_FORM_KEYS` (id документов заранее не известны) — `clear_stage_form_state()` дополнительно чистит их по префиксу при каждом открытии/закрытии диалога этапа, иначе они тянутся из ранее открытого этапа (тот же класс бага, что и у `d_*`/`td_*`, см. выше).
- Ветка Б (`CHANGES_PROTOCOL`/`ADDITIONAL_AGREEMENT`) в `calculate_buro_progress()` на момент той переработки не менялась — она касалась UI/данных, не формулы процента. ⚠️ **Устарело**: ветка Б с тех пор переписана, см. «Завершённая работа над документом возвращает проект к 100%» ниже.

### Фильтр «Только поставщики ОНПД» и табличный вид этапов (вкладка «Проекты»)

- Чекбокс `only_mandatory_sup` над фильтром поставщика (`project_dashboard.py::render_project_dashboard`) сужает и список поставщиков (`suppliers.is_mandatory`), и — при выбранном «Все» — список проектов ниже. ### Части вида сведений: `info_type_parts` + `project_item_part_details`

Виды сведений обязательных наборов заданы регламентом, но один вид иногда включает несколько видов информации, которые поставщик передаёт по отдельности: тогда на вид сведений заключается не один протокол, а несколько. **Часть вида сведений = единица, которой соответствует один протокол.**

Раньше части жили в составе проекта (`project_item_parts`, привязка к `item_id`), из-за чего один и тот же разбитый вид приходилось заводить заново каждому поставщику. Теперь состав частей — свойство справочника, а условия передачи — свойство проекта:

- **`info_type_parts`** (`part_id`, `info_id` → `info_types` CASCADE, `part_name`, `sort_order`; UC `unique_info_part_name(info_id, part_name)`) — только идентичность части. Общая для всех поставщиков: раз вид сведений одинаков, то и его дробление тоже.
- **`project_item_part_details`** (`detail_id`, `item_id` → `project_items`, `part_id` → `info_type_parts`, `provision_right`, `format`, `update_period`, `meta_days`, `meta_method`, `data_days`, `data_method`; UC `unique_item_part_detail(item_id, part_id)`) — как ЭТОТ поставщик передаёт ЭТУ часть. **Наличие строк по `item_id` и означает «поставщик разбил вид сведений»** — на этом признаке держатся разворот таблицы состава и отчёт №9.
- `project_items` получил `format`/`update_period`: раньше они были только глобальными в `info_types` и не могли отличаться у разных поставщиков. Цепочка наследования везде одна: **деталь части → `project_items` → `info_types`** (`COALESCE(pd.X, pi.X, i.X)`).
- **Значения копируются лениво**, при первом открытии блока «✂️ Параметры передачи по частям» (`project_dashboard.py::render_part_details_manager`): `INSERT ... SELECT ... ON CONFLICT DO NOTHING` не затирает отредактированное и довозит части, добавленные в справочник позже. Момента «создания первой части внутри проекта» больше не существует — части создаются в справочнике.
- **Управление частями** — `datasets_tab.py::info_type_parts_dialog` («🗄️ Наборы → 📄 Виды сведений → ✂️ Части»): добавление, переименование, перестановка ⬆⬇, удаление. Удаление занятой части блокируется со списком затронутых поставщиков. Ключи session_state содержат id, поэтому чистятся по префиксу `itp_` (тот же класс бага, что у `d_*`/`td_*`).
- Миграции: `a4f7c21e8b93` (создание + перенос данных + перевешивание FK `project_document_items.part_id`), `b8d3e05a1c47` (удаление `project_item_parts`). При переносе одноимённые части разных проектов схлопываются в одну глобальную, `sort_order` пересчитывается через `row_number()` — у разных проектов нумерация своя и при слиянии конфликтует. **Обратный маппинг `part_id` невосстановим**, откат только из дампа.

### `affected_item_ids`: массив объектов `{item_id, part_id}`

Технологический этап умеет нацеливаться на часть вида сведений: у части свои сроки размещения, и опубликована она может быть отдельно. Формат `project_stages.affected_item_ids` сменился с `[18, 105]` на `[{"item_id": 18, "part_id": null}, {"item_id": 105, "part_id": 7}]` (миграция `c5e9f1a73d20`).

- **`part_id = NULL` означает «вид сведений целиком»** (все его части). Так трактуются все записи после конвертации, поэтому смысл исторических данных не изменился и проценты готовности не упали.
- **Завершённость по частям**: вид сведений считается опубликованным, когда закрыт этапом целиком либо когда закрыты все части, заведённые у этого поставщика (`sync_project_status`, отчёт №9).
- Развернуть массив теперь можно только через `jsonb_array_elements` + `(aff ->> 'item_id')::int`. Оператор `@>` с числом на массиве объектов **не работает** — оба guard'а перед удалением состава (`project_dashboard.py`, `suppliers_tab.py`) переписаны на `EXISTS`.
- Затронуто десять мест: `technology_tab.py` (мультиселект, SLA, охват в карточке и таблице), `data_provider.py`, `analytics_tab.py` (лог просрочек), `project_utils.py`, `reports.py`, оба guard'а. `stages_tracking.py:116` остался на старом формате — файл orphaned, приложением не импортируется.
- В снапшоте аналитики `info_name` технологической ветки теперь содержит подпись части (`вид → часть`), если этап нацелен на неё.

### Завершённая работа над документом возвращает проект к 100% (ветка Б `calculate_buro_progress`)

Внесение изменений и допсоглашение — работа НАД уже подписанным документом: пока она идёт, проект временно отходит от завершённого состояния, а когда закончена — снова выполнен на 100%.

Раньше вес был жёстко закреплён (5% на `CHANGES_PROTOCOL` + 5% на `ADDITIONAL_AGREEMENT`), поэтому проект с одним типом этапа упирался в потолок 95% даже после его завершения: недостающие 5% резервировались под этап, которого в проекте нет. Наблюдалось как **97,5% у полностью завершённого проекта** — полусумма бюро-трека (95) и тех-трека (100) в `calculate_project_progress`.

- Вес делится между теми этапами ветки, которые в проекте **реально есть**: один → 10%, оба → по 5%.
- Завершение всех этапов ветки даёт 100%, но только если подписаны все документы проекта; иначе `100 × docs_signed / docs_total` — незакрытый документ означает, что изменения не доведены до подписания.
- Проверено на «Первичное подключение БелПСХАГИ»: было 95, стало 100; при `CHANGES_PROTOCOL` в работе — 99; при 3 из 4 подписанных документов — 75.

Проект-соглашение (первичное подключение) и проект-протокол (передача видов сведений) проходят разные по смыслу этапы, хотя раньше пользовались общими:

Реестр соглашений (`reports.py:77`) намеренно оставлен на `CONTRACT_SIGNED` — он только про соглашения, а миграция их не трогает.

В форме реквизитов текущий проект из проверки исключён — иначе галочка блокировалась бы у того проекта, который её и держит.

### Охват протокола в подписях документов

Протокол показывается не одним номером, а с указанием вида сведений (или части), к которому относится: «Протокол 1 — сведения о гостиницах». Пустой охват `project_document_items` означает «весь проект», поэтому вместо неинформативной пометки подставляется его состав. **У соглашения охват не показывается** — оно у поставщика одно.

Задействовано шесть мест, все они читают охват одним и тем же подзапросом (явный охват → состав проекта): `shared_components.py` (карточка поставщика и паспорт проекта), `reports.py` (реестр соглашений), `suppliers_tab.py` (Наборы), `bureaucracy_tab.py` (карточка документа и подпись в форме этапа), `datasets_tab.py` (справочник видов сведений).

Порядок документов везде по номеру, а не по дате или `sort_order`: протоколы нумеруются последовательно и читаются подряд. `doc_number` — текст, поэтому числовая часть извлекается отдельно (`NULLIF(regexp_replace(...,'\D','','g'),'')::bigint`), иначе «10» встаёт перед «8».

Переведён на этот источник; дата берётся из `doc_date` с запасным вариантом по дате закрытия этапа, документ без скана показывается текстом.

### Раздел «🕘 Последние события» (`src/ui/analytics/events.py`)

Лента этапов обоих треков между «Прогресс проектов» и «Отчёты». В карточке: поставщик, охват, этап с номером итерации, комментарий (пустой заменяется названием этапа). Фильтры по поставщику и периоду (неделя / месяц / всё время).

- Данные берутся из общего снапшота — отдельный запрос не нужен. Технологическая ветка развёрнута по `affected_item_ids`, поэтому этап на N видов сведений приходит N одинаковыми строками: **в ленте они схлопываются в одно событие**, виды склеиваются в одну подпись. Ключ события — `project_id|track_type|stage_code|iteration_count`.
- Охват по смыслу этапа: у бюрократического — название проекта, у технологического — виды сведений (или их части).
- **Выполненные** датируются `actual_end`, **этапы в работе** — сегодняшним днём (они актуальны сейчас, независимо от того, когда начались); дата начала выводится отдельным бейджем «⏳ В работе с …». Внутри одного дня активные идут выше выполненных, между собой — по дате начала, дольше идущие сверху.

### Автоперевод «Планируется» → «В работе» (`analytics_tab.py::_sync_planned_to_active`)

Этап с наступившей плановой датой старта сам переходит в «В работе». Отдельного планировщика в приложении нет, поэтому `UPDATE` выполняется **при заходе в Аналитику**, рядом с уже существующей `_sync_overdue_log_internal()`: этап «оживает» не в полночь, а когда кто-то открыл вкладку. Это осознанно — задача была в том, чтобы такие этапы стали видны в аналитике, а не в точности момента перехода.

- `actual_start` проставляется намеренно, через `COALESCE` (уже указанную дату не затирает). Без неё этап не попал бы ни в ленту событий, ни в расчёт SLA, а форма этапа блокирует это поле для статуса «Планируется». У просроченного по старту этапа дата встанет задним числом — принятый компромисс, правится в карточке этапа.
- `clear_cache()` вызывается только когда строки действительно обновились (`res.rowcount`): снапшот аналитики кэширован, иначе «ожившие» этапы появились бы лишь после истечения TTL.
- Ошибка глушится в `stderr` и не роняет вкладку — как и в соседней синхронизации просрочек: падение аналитики из-за вспомогательного `UPDATE` было бы хуже самой проблемы.
- ⚠️ **Первое срабатывание после выката** переведёт разом все подходящие этапы, включая давно просроченные по старту. Стоит заранее прикинуть объём: `SELECT count(*) FROM project_stages WHERE micro_status = 1 AND planned_start <= CURRENT_DATE AND actual_end IS NULL`.

### Миграции этой серии (порядок применения)

`a4f7c21e8b93` → `b8d3e05a1c47` → `c5e9f1a73d20` → `d7b4e28c9f15`

Все четыре переписывают живые данные. Перед каждой — бэкап: сервис `db-backup` в `docker-compose.yml` (`docker compose exec db-backup /usr/local/bin/backup.sh`, дамп в `./backups/daily`, ротация оставляет 7 последних — рабочий снимок стоит скопировать за пределы этой папки).

**История с потерей бэкапов** (исправлено, но знать полезно): в `backup.sh` стоял `set -e`, поэтому падение `pg_dump` завершало скрипт до входа в цикл ожидания, `restart: unless-stopped` поднимал контейнер заново — краш-луп с попыткой дампа каждые несколько минут, при котором ротация «оставить 7 последних» вытесняла настоящие дампы пустыми файлами. Так и потерялась вся история, пока `.env` ещё указывал на выведенный из эксплуатации Supabase.

Теперь скрипт переживает неудачу: `pg_dump` обёрнут в проверку, неудачный или пустой файл удаляется, **ротация идёт только после удачного дампа**, цикл продолжается. Расписание привязано ко времени суток (`BACKUP_HOUR`, по умолчанию 3:00), а не `sleep 86400` от старта — иначе при каждом перезапуске контейнера время бэкапа съезжало. Две тонкости на будущее: образ собран на alpine (BusyBox), поэтому `%-H` использовать нельзя — только `%H`; и часы обязаны разбираться как `10#$H`, иначе «08»/«09» в POSIX-арифметике трактуются как восьмеричные и роняют счёт (то есть скрипт ломался бы каждый день с полуночи до 10 утра).

Если в `backups/daily` всё же появятся файлы нулевого размера — смотреть `docker compose logs db-backup`; при смене реквизитов БД контейнер нужно пересоздать (`docker compose up -d --force-recreate db-backup`), обычный restart не перечитывает `.env`.
