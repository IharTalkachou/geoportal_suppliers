# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Streamlit web app for managing suppliers, projects, and data-provision workflows for the National Geoportal (Belarus NSDI — НИПД). Backend is PostgreSQL (Supabase-hosted), accessed via SQLAlchemy Core (raw `text()` SQL, not the ORM query layer) plus a small set of Alembic-managed models for schema tracking.

## Commands

### Run locally (Docker — primary way this app is deployed)
```bash
docker compose up -d --build          # build & start db, app, nginx, db-backup
docker compose logs -f app            # tail app logs
docker compose restart app            # restart after code change (folder is bind-mounted)
docker compose down                   # stop & remove containers
```
App: http://localhost:8501 · pgAdmin/DB access: see `.env` for credentials.

### Run locally without Docker (debugging)
```bash
pip install -r requirements.txt
streamlit run src/app.py --server.port 8501
```
**Note:** `streamlit run src/app.py` puts `src/` on `sys.path`, which is why almost every file under `src/` uses bare imports (`from config.cache import query_db`, `from ui.suppliers_tab import ...`) rather than `from src.config...`.

### Database migrations (Alembic)
Alembic is run from the **project root** (not `src/`), so `alembic/env.py` and any manually-run migration script must import via `src.config.database` / `src.models.tables` (root-relative), while the app itself imports the same modules bare (`config.database`). Both styles exist in this repo — see "Known inconsistencies" below.

```bash
alembic revision --autogenerate -m "description"   # generate migration from tables.py vs live DB diff
alembic upgrade head                                # apply pending migrations
alembic downgrade -1                                # roll back one revision
```
**Always inspect an autogenerated migration before applying it.** Alembic's autogenerate diffs `src/models/tables.py` against the live DB schema — if a table/column/index/comment exists in the DB but isn't declared in `tables.py`, autogenerate will propose *dropping* it. This has already happened once in this repo: an incomplete `tables.py` produced a migration that would have deleted 13 real indexes and every column/table comment. Read the generated `upgrade()`/`downgrade()` body; if it contains `drop_index`/`comment=None` changes you didn't intend, the fix is to update `tables.py` (add the missing `Index(...)` / `comment=...`) and regenerate, not to hand-edit the migration.

There is no test suite and no lint/build step configured in this repo.

## Architecture

### Request/session lifecycle
1. `src/app.py` is the sole entrypoint. It calls `load_settings()` (DB-backed feature flags: maintenance mode, session timeout), then handles auth.
2. **Auth is not Streamlit's built-in session state alone** — it's backed by a custom file-based token store (`config/session_store.py`) so login survives page refresh (`Ctrl+R`) and browser reopen within a timeout window. Tokens are stored as JSON files under `SESSION_DIR` (`app_data/sessions/` in Docker), keyed by a UUID passed via `st.query_params["session"]`. Each token file also carries a browser/OS fingerprint + IP; mismatches are logged as `SESSION_HIJACK_ATTEMPT` but the original session is *not* invalidated (only that request is denied).
3. `config/session_store_2.py` is an **older, simplified variant** of the same module (no IP check, no `sync_session_to_disk`, different signatures). `app.py` imports from `session_store` (not `_2`) — treat `_2` as dead code unless told otherwise.
4. Navigation is a flat `st.segmented_control` with 5 top-level sections wired in `app.py`: Поставщики (`suppliers_tab`), Наборы (`datasets_tab`), Проекты (`project_dashboard`), Заявки (`requests_tab`), Аналитика (`analytics_tab`). An admin panel (`admin_panel.py`) is reached via a header button, gated by `require_role("admin")`.
5. Every DB read goes through `config/cache.py::query_db()`, wrapped in `@st.cache_data(ttl=120)`. Every write path follows the same shape: build params → `session.execute(text(sql), params)` → `session.commit()` → `clear_cache()` → `st.rerun()`. `clear_cache()` must be called after commit or stale cached reads will be shown.

### Data model: raw SQL vs ORM
Almost all business logic uses **raw parameterized SQL** via `sqlalchemy.text()`, not the ORM session query API. `src/models/tables.py` exists mainly so **Alembic** can autogenerate migrations — it is kept in sync with the live schema (34 tables, custom Postgres ENUMs, arrays, indexes, comments) but is barely used at runtime (only `AppSetting` and `AuditLog` are actually imported/queried as ORM classes, in `settings_handler.py` and `maintenance.py`). When adding a column/table, update **both** the live DB (via an Alembic migration) and `tables.py` — they are the source of truth for autogenerate diffing, not for query logic.

Custom Postgres ENUM types (`applicant_category`, `org_target_type`, `request_status`, `data_provision_type`, `restrictions`, `definitions`) are defined with `create_type=False` in `tables.py` because they already exist in the DB and are cast explicitly in raw SQL (`CAST(:val AS applicant_category)`) rather than created/managed by SQLAlchemy.

### The "single stages table" refactor
Project stages used to be split across a bureaucracy-specific table and a technology-specific table; they were later merged into one shared `project_stages` table (see git history: "объединение стеков в одну таблицу"). The distinction between the two tracks is now done at the *data* level, not the schema level:
- `stages.track_category` = `'1. Документарный'` (bureaucracy) or `'2. Технологический'` (technology).
- For technology-track rows, `project_stages.affected_item_ids` (JSONB array) lists which `project_items.item_id` the stage applies to — queried via `jsonb_array_elements_text(...)::int` / `CROSS JOIN LATERAL`.
- `item_stages_old` is the **pre-refactor** technology-stage table, kept only for historical FK references from `stage_documents`; it is not written to by current code.
- `bureaucracy_tab.py` and `technology_tab.py` both operate on `project_stages` with near-identical auto-iteration/auto-close logic (`_resync_buro_iterations` / `_resync_tech_iterations`), filtered by `track_category` — read both together when changing this logic, they tend to drift.
- `utils/project_utils.py::sync_project_status()` recomputes `projects.status` from the current state of `project_stages` after every stage save; it's called explicitly after each CRUD, not via a DB trigger.

### Reactive CRUD pattern
Tables/forms across `suppliers_tab.py`, `datasets_tab.py`, `project_dashboard.py`, `bureaucracy_tab.py`, `technology_tab.py` follow the same shape: a filterable `st.dataframe` for browsing, plus `@st.dialog(...)`-based modal forms for create/edit (see `bureaucracy_tab.py::stage_mgmt_dialog` for the fullest example — auto-computed `planned_end` from stage duration, dependent staff/document sub-sections). Prefer this `st.dialog` pattern over inline forms when adding new CRUD screens — it's what the rest of the codebase does.

### Analytics module (`src/ui/analytics/`)
`analytics_tab.py` is a thin router; the actual logic is split by concern:
- `data_provider.py::get_analytics_snapshot()` — single cached query that UNIONs bureaucracy-track and technology-track stage rows (expanding `affected_item_ids` for the latter) into one flat DataFrame. Most analytics views consume this instead of writing their own joins.
- `kpi_logic.py` — task-level KPI cards/grouping (SLA proximity coloring, badges).
- `calendar.py` — `streamlit_calendar` deadline view.
- `staff.py` — per-employee workload views.
- `progress_math.py` — progress % calculations per track (`calculate_buro_progress`, `calculate_tech_progress`, `calculate_project_progress`) and the "traffic light" summary chart.
- `heatmap.py` — detailed delay heatmaps (referenced as still-in-progress in `analytics_tab.py` comments).
- `reports.py` — exports/registries (agreement registry, meeting minutes, Excel exports).
- `report_docx.py` — monthly NIPD report builder (`.docx` generation via `python-docx`). Report sections/blocks are stored as JSONB in `reports_monthly.sections_data`, driven by the `DEFAULT_SECTIONS` template dict at the top of the file. Once a report is fixed (`fixed_at` set via the "Зафиксировать" dialog), it becomes read-only; `get_report_period_bounds()` uses the previous report's `fixed_at` (or the 1st of the month if none) as the start of the next collection period — this is load-bearing logic, don't change the fixing flow without checking it.
- `analytics_tab.py::_sync_overdue_log_internal()` runs on every load of the Analytics tab: it inserts newly-overdue stages into `overdue_log` (`ON CONFLICT DO NOTHING`, so it's idempotent) for both tracks.

- `src/ui/stages_tracking.py` — an older generic stage tracker, superseded by `bureaucracy_tab.py`/`technology_tab.py`. Not imported anywhere.

Don't assume these are dead ends to fix; confirm with a repo-wide grep for the module name before editing, since this list can go stale.

### Known inconsistencies to be aware of
- **Import style split**: most of `src/` uses bare imports (`config.*`, `models.*`, `ui.*`) because Streamlit runs with `src/` as the path root. But `src/utils/maintenance.py` and `alembic/env.py` use root-relative imports (`src.config.*`, `src.models.*`) because they're invoked from the project root. If you add a new module that needs to work in both contexts, check how it's actually invoked rather than copying a neighboring file's import style.
- `requirements.txt` is saved as UTF-16 — reading it with a plain UTF-8 tool may render it unreadable; decode as UTF-16 if you need to parse it programmatically.
- There are two Dockerfiles: `dockerfile` (dev, used by `docker-compose.yml`) and `dockerfile copy for prod` (used by `docker-compose.prod.yml`) — check which compose file you're targeting before editing build steps.

## Auth & roles
Three roles, hierarchical: `user` < `editor` < `admin` (see `config/auth.py::require_role()`). Role gates are enforced per-render-function (e.g. `render_admin_panel` calls `require_role("admin")` at the top), not via a central router — new admin-only screens must call this themselves.

All login/logout and CRUD actions that call `log_action()` write to `audit_log` over a **separate** DB session/connection from the business transaction, so audit writes never roll back with a failed business transaction and never block it on error (failures are swallowed and printed to stderr).
