# Перенос приложения на новую ВМ

Пошаговый порядок переноса прода на другую виртуальную машину (Linux, Docker Compose).
Раздел 1 написан для сисадмина, его можно переслать целиком. Остальные разделы
выполняет владелец приложения.

## Как устроен перенос

| Что | Как переносится |
|---|---|
| Код | `git clone` из GitHub, тот же коммит, что на старой ВМ |
| Настройки | копируются вручную: файлы вне git (`.env`, `.streamlit/config.toml`) |
| Данные | дамп БД на старой ВМ → восстановление на новой. Docker-том не копируется. |

Простой для пользователей — 30–60 минут, в основном на проверки: база небольшая (дамп меньше 1 МБ).

**Обозначения ниже:**
- `СТАРАЯ` — текущая ВМ, `172.30.12.33`;
- `НОВАЯ` — адрес новой ВМ;
- `~/geoportal_suppliers` — каталог проекта; подставьте фактический путь.

Все команды `docker compose` выполняются **из каталога проекта**: там лежат `docker-compose.yml` и `.env`.

## 1. Заявка сисадмину

> Для развёртывания веб-приложения (Python/Streamlit + PostgreSQL в Docker) нужна ВМ со следующими параметрами.
>
> **Система и ресурсы**
> - Linux x86_64: Ubuntu 22.04/24.04 LTS или Debian 12.
> - Ресурсы: 2 vCPU, 4 ГБ RAM, 40 ГБ диска.
> - Статический IP в локальной сети; при возможности — DNS-имя.
> - Синхронизация времени (NTP).
>
> **Программы**
> - Docker Engine из официального репозитория Docker (download.docker.com), не пакет `docker.io` из дистрибутива.
> - Плагин Docker Compose v2: `docker compose version` должен показать 2.20 или новее.
> - git.
>
> **Доступ**
> - Учётная запись с доступом по SSH, добавленная в группу `docker`.
>
> **Входящие соединения**
> - 22/tcp (SSH) — из сети администраторов.
> - 8501/tcp — из локальной сети пользователей (веб-интерфейс).
> - 80/tcp и 443/tcp — только если приложение будет публиковаться через nginx с HTTPS.
>
> **Исходящие соединения** (для сборки и обновления)
> - github.com — получение кода (`git pull`).
> - Docker Hub: `registry-1.docker.io`, `auth.docker.io`, `production.cloudflare.docker.com`.
> - PyPI: `pypi.org`, `files.pythonhosted.org`.
>
> Если выход в интернет идёт через прокси, настройте прокси для демона Docker и сообщите его адрес: он понадобится и при сборке образа. Если на выходе есть TLS-инспекция (антивирус подменяет сертификаты), тоже сообщите.
>
> **На время переноса**
> - Доступ по SSH/scp между старой (172.30.12.33) и новой ВМ, либо с рабочей станции к обеим.
>
> **Резервное копирование**
> - Желательно снапшоты ВМ или копирование каталога с дампами БД на внешнее хранилище.

## 2. Аудит старой ВМ (за день-два до переноса)

Цель — убедиться, что всё нужное для работы лежит либо в git, либо в списке файлов для переноса.

```bash
cd ~/geoportal_suppliers
git status                                # должно быть "nothing to commit, working tree clean"
git log -1 --oneline                      # коммит, на котором работает прод, - записать
git remote -v                             # откуда тянется код
docker compose ps                         # какие сервисы Up, какие порты, нет ли Restarting
docker compose exec app alembic current   # версия схемы БД ...
docker compose exec app alembic heads     # ... должна совпадать с этой
grep DB_HOST .env                         # см. ловушку ниже
ls -la .env .streamlit/config.toml certbot/conf backups/daily
crontab -l; sudo crontab -l               # нет ли заданий, относящихся к приложению
```

На что смотреть:

- **`git status` не чистый** — на ВМ есть правки мимо git, например открытый порт в `docker-compose.yml`. Их нужно закоммитить или записать, иначе на новой ВМ их не будет.
- **`alembic current` ≠ `alembic heads`** — есть непримененные миграции. Сначала применить на старой ВМ (`docker compose exec app alembic upgrade head`), потом переносить.
- ⚠️ **`DB_HOST` — IP-адрес, а не `db`.** Главная ловушка переноса: скопированный `.env` будет указывать новой ВМ на базу старой, и новое приложение молча продолжит писать в старую БД. На новой ВМ `DB_HOST` должен быть `db` — это имя сервиса внутри Compose, от адреса машины оно не зависит.
- **`nginx` в состоянии `Restarting`** — нет сертификатов в `certbot/conf/live/localhost/`. Если пользователи ходят на порт 8501, nginx не используется и переносить его не обязательно.
- **Задания в crontab**, относящиеся к приложению, нужно повторить на новой ВМ.

### Что переносится вручную (не хранится в git)

| Файл | Нужен? | Зачем |
|---|---|---|
| `.env` | **обязательно** | реквизиты БД, `APP_SECRET_KEY`; на новой ВМ поправить `DB_HOST=db` |
| `.streamlit/config.toml` | **обязательно** | светлая тема и отключённое слежение за файлами; без него интерфейс изменится |
| `certbot/` | если работает HTTPS через nginx | сертификаты |
| `backups/` | по желанию | история дампов; на новой ВМ бэкапы начнутся заново |
| `app_data/sessions/` | не нужно | пользователи просто войдут заново |

## 3. Подготовка новой ВМ (заранее, без простоя)

```bash
git clone https://github.com/IharTalkachou/geoportal_suppliers.git ~/geoportal_suppliers
cd ~/geoportal_suppliers
git checkout <коммит из аудита>     # если старая ВМ на последнем main - этот шаг не нужен
```

Если репозиторий приватный, для доступа лучше завести **deploy key** (SSH-ключ только на чтение, привязанный к одному репозиторию: GitHub → Settings → Deploy keys) и клонировать по SSH-адресу. Личный токен на сервере оставлять не стоит.

Скопировать файлы вне git. Команды выполняются на новой ВМ; если прямого доступа между ВМ нет — через рабочую станцию:

```bash
scp СТАРАЯ:~/geoportal_suppliers/.env .
mkdir -p .streamlit
scp СТАРАЯ:~/geoportal_suppliers/.streamlit/config.toml .streamlit/
```

Открыть `.env` и выставить `DB_HOST=db`. Остальные значения оставить как есть: имя роли и пароль БД на новой ВМ будут те же.

Собрать образы. Это заодно проверит, что сисадмин открыл доступ к Docker Hub и PyPI:

```bash
docker compose build
```

**Ничего не запускать.** Первый запуск — в разделе 4.

## 4. Перенос данных (окно простоя)

### 4.1. Предупредить пользователей о простое

### 4.2. Старая ВМ: остановить приложение, БД оставить работать

```bash
cd ~/geoportal_suppliers
docker compose stop app nginx
```

После этого в БД никто не пишет: дамп будет последним состоянием данных.

### 4.3. Старая ВМ: снять дамп и подсчитать строки

```bash
docker compose exec db-backup sh -c 'pg_dump -h "$DB_HOST" -p "$DB_PORT" -U "$DB_USER" -d "$DB_NAME" -Fc -f /backups/migration.dump'
ls -la backups/migration.dump
sha256sum backups/migration.dump      # записать контрольную сумму
```

Почему не `backup.sh`: после дампа этот скрипт уходит в бесконечный цикл ожидания следующего ночного бэкапа, и команда не вернёт управление.

Подсчёт строк по всем таблицам — эталон для сверки после переноса:

```bash
cat > /tmp/counts.sql <<'SQL'
SELECT table_name,
       (xpath('/row/c/text()',
              query_to_xml(format('SELECT count(*) AS c FROM public.%I', table_name),
                           false, true, '')))[1]::text AS rows
FROM information_schema.tables
WHERE table_schema = 'public' AND table_type = 'BASE TABLE'
ORDER BY table_name;
SQL
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -At -F " "' < /tmp/counts.sql > counts_old.txt
cat counts_old.txt
```

### 4.4. Перенести дамп и эталон на новую ВМ

```bash
# на новой ВМ, из каталога проекта
mkdir -p backups
scp СТАРАЯ:~/geoportal_suppliers/backups/migration.dump backups/
scp СТАРАЯ:~/geoportal_suppliers/counts_old.txt .
scp СТАРАЯ:/tmp/counts.sql /tmp/
sha256sum backups/migration.dump      # должна совпасть с записанной
```

### 4.5. Новая ВМ: поднять только БД и очистить её

```bash
docker compose up -d db
docker compose ps db                  # дождаться (healthy)
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1 -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;"'
```

Зачем очищать пустую базу: при первом старте контейнер `db` автоматически выполняет `db/schema.sql`. Это устаревшая схема на 15 таблиц, а в рабочей базе их около 40. Если её не убрать, восстановление наткнётся на уже существующие таблицы.

### 4.6. Новая ВМ: восстановить дамп

```bash
docker compose run --rm db-backup sh -c 'pg_restore -h "$DB_HOST" -p "$DB_PORT" -U "$DB_USER" -d "$DB_NAME" --no-owner --no-privileges /backups/migration.dump'
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "VACUUM ANALYZE;"'
```

⚠️ **Восстанавливать только через контейнер `db-backup`**, не через `db`. Дамп сделан утилитой `pg_dump` версии 17: образ бэкапов собран на `postgres:17-alpine`, формат архива 1.16. Сама БД работает на `postgres:16`, и её `pg_restore` такой файл не прочитает: `unsupported version (1.16) in file header`.

Нормальный результат — без вывода. Если в конце есть строка `errors ignored on restore: N` — остановиться и разобрать ошибки до запуска приложения.

### 4.7. Новая ВМ: сверить строки с эталоном

Сверять **до** запуска приложения: при входе в «Аналитику» оно само меняет данные (автоперевод этапов в «В работе», журнал просрочек), а вход пользователя пишет в журнал действий.

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -At -F " "' < /tmp/counts.sql > counts_new.txt
diff counts_old.txt counts_new.txt && echo "Совпадает"
```

Пустой `diff` (и «Совпадает») — данные перенесены полностью.

## 5. Запуск и проверка

```bash
docker compose up -d
docker compose ps                          # app, db, db-backup - Up
docker compose logs --tail=50 app          # без трассировок ошибок
docker compose exec app alembic current    # совпадает с alembic heads
docker compose exec app date               # минское время
docker compose logs db-backup | tail -5    # "✅ Ежедневный бэкап создан"
```

Если nginx в состоянии `Restarting` — нет сертификатов (см. аудит). Пока HTTPS не настроен, его можно остановить: `docker compose stop nginx`.

Проверка в браузере — `http://НОВАЯ:8501`:

- [ ] вход под своей учётной записью;
- [ ] открываются все пять разделов: Поставщики, Наборы, Проекты, Заявки, Аналитика;
- [ ] есть последние внесённые записи (например, самая свежая заявка) — значит, дамп свежий;
- [ ] карточка проекта: этапы в карточках, таблице и на диаграмме Ганта;
- [ ] «Аналитика → Отчёты → 9» — выгрузка в Word скачивается и открывается;
- [ ] админ-панель открывается.

## 6. Переключение пользователей и откат

1. Сообщить пользователям новый адрес.
2. На старой ВМ остановить всё, **сохранив данные**:
   ```bash
   docker compose stop
   ```
   ⚠️ Не `docker compose down -v`: флаг `-v` удаляет том с базой данных.
3. Старую ВМ держать нетронутой минимум две недели.

**Откат:**
- **пока пользователи не работали на новой ВМ** — на старой `docker compose start`, и всё как было;
- **после начала работы** — данные, внесённые на новой ВМ, есть только там. Их придётся перенести обратно тем же порядком (раздел 4 в обратную сторону) или принять их потерю.

## 7. После переноса

- Сообщить новый адрес для документации: в `CLAUDE.md` и `README.md` сейчас указан `172.30.12.33`.
- На машине разработчика поправить `DB_HOST` в локальном `.env`.
- Убедиться, что на новой ВМ несколько ночей подряд появляются дампы в `backups/daily/`.
- Через две недели, если всё работает, вывести старую ВМ: `docker compose down -v`, удалить каталог проекта, сообщить сисадмину.
